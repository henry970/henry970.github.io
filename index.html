Inside my OrangeHRM test suite: Selenium, pytest and GitHub Actions

A walkthrough of my public OrangeHRM automation repo: how it is structured, how CI runs it, and what I would improve next.

OrangeHRM's public demo is a good playground for UI automation: a real login, real navigation and several modules to cover. I used it to build a small but complete Selenium suite you can read on GitHub.

The layout

The suite follows the Page Object Model. Locators live in their own classes (loginLocators.py, Admin_page_locators.py and so on), and the page classes hold the actions a user can take. Tests only call those actions.

  • Locators: one class per module (Login, Admin, PIM, Leave, Time).
  • Pages: methods like enter_username() and click_admin_button().
  • Tests: one file, test_Orange.py, with a test per module.

One browser, one login

A module-scoped fixture starts headless Chrome once and a second fixture opens the login page, so every test shares the same session:

@pytest.fixture(scope="module")
def driver_setup():
    chrome_options = Options()
    chrome_options.add_argument("--headless")
    chrome_options.add_argument("--no-sandbox")
    chrome_options.add_argument("--window-size=1920x1080")
    driver = webdriver.Chrome(service=Service(ChromeDriverManager().install()), options=chrome_options)
    driver.implicitly_wait(20)
    yield driver
    driver.quit()


@pytest.fixture(scope="module")
def login(driver_setup):
    login_page = LoginPage(driver_setup)
    login_page.open_login_page("https://opensource-demo.orangehrmlive.com/web/index.php/auth/login")
    return login_page

Waiting for the page, not guessing

Page actions wait for the element before touching it, which removes most flakiness on a slow demo server:

def enter_username(self, username):
    username_field = WebDriverWait(self.driver, 20).until(
        EC.presence_of_element_located(ActionPageLocators.USERNAME_FIELD))
    username_field.send_keys(username)

CI on every push

A GitHub Actions workflow installs the dependencies, runs pytest and uploads the HTML report, even when a test fails:

- name: Run tests
  run: |
    source venv/bin/activate
    pytest --html=report.html -p no:warnings

- name: Upload HTML report
  if: always()
  uses: actions/upload-artifact@v3
  with:
    name: pytest-report
    path: report.html

The latest saved report shows all five tests passing in 55 seconds.

What I would improve next

Reviewing your own old code is a good habit. Here is my list for this repo:

  • Add assertions. Each test should check something visible, like the dashboard header after login, not only that the clicks worked.
  • Replace absolute XPaths with shorter, attribute-based locators so a layout change does not break every test.
  • Remove the fixed time.sleep() after login and wait for the dashboard instead.
  • Add negative tests such as a wrong password and empty fields.

Testing core banking flows: the checklist I use

Account management, transfers, beneficiaries and transaction status: what I check end to end before a banking release.

Most of my work has been on payments and banking products. In that world a bug is rarely a crash. It is a transfer that shows "successful" but never lands, or a balance that is off by one decimal place. This is the checklist I work through.

1. Follow the money end to end

I test each workflow from initiation to completion, not screen by screen. For a transfer that means: create, authorise, process, settle, notify, and confirm the receipt and both balances.

2. Account management

  • Opening, updating and closing accounts with valid and invalid data.
  • Restrictions: frozen, dormant or limited accounts must block the right actions.
  • Profile changes that need re-verification really do trigger it.

3. Transfers and transaction processing

  • Amounts at and around the limits: zero, the minimum, the daily limit, one unit over.
  • Insufficient balance, duplicate submissions and retries.
  • Status updates in the right order, with no jumps backwards.

4. Beneficiary management

Adding, editing and deleting beneficiaries, name enquiry before saving, and making sure a deleted beneficiary cannot still receive funds from a saved shortcut.

5. Data consistency

The same transaction must show the same amount, status and reference in the app, the API response, the statement and the admin view. When two of them disagree, I raise it even if the user-facing screen looks fine.

6. The API underneath

With Postman I validate endpoints, payloads, status codes, field-level validation, authentication and error messages. Many UI bugs are easier to prove at the API layer.

7. Regression and release

Every fix and feature gets a regression pass on the critical flows, then a smoke test during release validation to confirm that login, balance, transfer and history still work in the live build.

Why I built PerfPilot, a load tester inside a Chrome extension

JMeter is powerful but heavy for a quick check. Here is how I designed a compact, browser-based alternative.

I like JMeter, but setting it up for a five-minute "is this endpoint slow?" check always felt like too much. I wanted something that lives where I already work: the browser. That became PerfPilot.

Design rule: stay small

PerfPilot is a compact popup, not a full-screen workspace. Every feature had to fit a small window: pick a request, choose Quick or Full mode, set the load, run.

What it does

  • Recording to capture real requests instead of typing them in.
  • Variables and timers so tests behave more like real users.
  • Run history to compare today's numbers with last week's.
  • Results analysis right in the popup.

Working with JMeter, not against it

For bigger runs, PerfPilot exports the test as a JMeter .jmx file. Start a test quickly in the browser, then hand the same scenario to a full JMeter setup when you need scale.

Reports people can share

Results export as a PDF with a branded cover page, so a test run can go straight into a release note or a client update.

What I learned

Building a testing tool changed how I test. When you have to decide what to show in a tiny popup, you learn which numbers actually matter: response times under load, error rates, and how both change as users increase.

Writing bug reports developers actually like

A good bug report gets fixed faster. This is the structure I use and the mistakes I avoid.

A bug report is a small piece of writing with one job: let a developer see the problem without asking you a single question. Here is the structure I use.

A title that says what broke

"Transfer fails" is a complaint. "Transfer to saved beneficiary returns 500 when amount has 3 decimal places" is a bug report. Include the feature, the action and the condition.

Steps anyone can repeat

Numbered, one action per step, starting from a known state: which account, which environment, which build.

Expected vs actual

Two short lines. The gap between them is the bug. If you can't write the expected result, check the requirement first.

Evidence

  • A screenshot or short screen recording.
  • The API request and response when the UI is hiding the real error.
  • Logs or the transaction reference, so the developer can find it in the backend.

Severity is not priority

Severity is how bad the impact is. Priority is how soon it should be fixed. A typo on the login page can be low severity but high priority before a launch.

Then follow through

Retest the fix on the build it shipped in, run regression around it, and close the bug with a note on what you verified.

Your first JMeter test plan, step by step

A practical way to plan, build and read your first load test without drowning in JMeter options.

JMeter can look overwhelming. You only need a handful of pieces to run a useful first load test.

1. Decide the question first

"Can login handle 200 users in 5 minutes with responses under 2 seconds?" is a test. "Let's load test the app" is not. Write the question, the target numbers and the endpoint before opening JMeter.

2. The minimum test plan

  • Thread Group: number of users, ramp-up time and loop count.
  • HTTP Request: the endpoint, method and body.
  • HTTP Header Manager: content type and auth token.
  • CSV Data Set Config: different test users, so you aren't hammering one account.
  • Listeners: a summary report while you build, then off during real runs.

3. Ramp up, don't spike

Start small, then increase users in steps. If response times jump at a certain level, you have found the interesting part of the system.

4. Run from the command line

The GUI is for building. For real runs use non-GUI mode, which uses far fewer resources:

jmeter -n -t login_test.jmx -l results.jtl -e -o report/

5. Read the right numbers

Look at the 90th and 95th percentile response times, not only the average, plus the error rate and throughput. An average of 800 ms can hide a slow tail that real users feel.

6. Report it plainly

One page: the question, the load you applied, the results against the target, and where things started to degrade.

What training new testers taught me about testing

Teaching QA through ConfixHub sharpened my own habits. These are the lessons I keep coming back to.

Through ConfixHub I've trained more than 200 people in QA and automation. Teaching something is the fastest way to find out how well you really understand it.

Start with thinking, not tools

New testers want to jump into Selenium. The ones who grow fastest first learn to read a requirement and ask "what could go wrong here?" Tools come easier after that.

Test cases are a writing skill

A test case someone else can run without help is harder to write than it looks. Clear steps, one expected result per case, and positive and negative scenarios side by side.

Automation is for repetition

Automate what you'll check again and again: regression, smoke tests, API rules. Keep exploratory testing human, because that is where the surprising bugs come from.

Practice on real apps

Demo sites like OrangeHRM give learners real logins, real navigation and real bugs to find. A project they can put on GitHub is worth more than a certificate alone.

Communication is half the job

Finding a bug is useless if nobody understands the report. I spend as much time on bug reporting and talking to developers as on the testing itself.

Shift-left testing: finding bugs before code is written

The cheapest bug is the one caught in a requirement review. How I bring testing earlier in Agile teams.

"Shift left" means moving testing earlier in the process. In practice, it means a tester is in the room before the first line of code.

Review requirements like test cases

For each user story I ask: what happens with empty input, the maximum value, a duplicate, an expired session, no network? If the story doesn't answer it, that's a gap to raise in refinement, not a bug to find in two weeks.

Write acceptance criteria together

When product, developers and QA agree on the criteria up front, everyone is building and testing against the same definition of done.

Test the API before the UI

APIs are usually ready first. Testing them with Postman while the screens are still being built catches business-rule bugs days earlier.

Automate smoke tests in the pipeline

A small automated suite that runs on every merge tells the team within minutes when something critical breaks.

Keep testing on the right too

Shift-left doesn't replace release validation. Smoke tests on the live build and regression on critical flows still matter, especially in fintech.

How I Structure a Selenium Python Framework

The folder layout, fixtures and habits that keep a Selenium suite easy to extend and easy to debug.

A good framework makes the next test easy to write and a failing test easy to understand.

Pages, tests and config live apart

Three folders: pages/, tests/ and config/. Tests never hold locators, and page objects never hold assertions.

One page object per screen

Each page class holds its locators and the actions a user can take. When the UI changes, I fix one file, not fifty tests.

Fixtures do the setup

A conftest.py fixture starts the browser and cleans up after. A command-line flag picks browser and environment, so the same suite runs locally and in CI.

Waits, never sleeps

Explicit waits for visible or clickable elements. Fixed sleeps make a suite slow and flaky at once.

Markers and reports

Tests are tagged smoke, regression or sanity. Failures save a screenshot and URL into an HTML report a developer can read without rerunning anything.

API Testing Best Practices with Postman & Newman

The checklist I run on payment APIs, from money rules and duplicate requests to ledger checks in CI.

A payment API can return 200 OK and still lose someone's money. This is the checklist I run before an endpoint ships.

The money rules

Zero, negative, tiny and huge amounts, extra decimals, more than the balance or limit. Rejected requests need clear errors and untouched balances.

Send it twice

Same reference or idempotency key: the money moves once. Then two at the same moment, to catch race conditions.

Follow the status and the ledger

Pending goes forward, never back. Debits equal credits, and balance, ledger and report all agree.

Wrong user, wrong token

No token, expired token, someone else's token. Nobody sees or moves money that isn't theirs.

Run it on every push

Collections live in Git and Newman runs them in CI, so a broken rule fails the pipeline, not a customer.

Mobile App Testing with Appium (Android & iOS)

How I keep Appium suites stable across devices, and the phone behaviours that hide the worst bugs.

Mobile bugs hide in the gaps between devices. Here's how I keep Appium suites useful instead of flaky.

Stable locators

Accessibility IDs on key elements work on both platforms and survive layout changes. XPath is the last resort.

Shared flows

One page-object interface over UiAutomator2 and XCUITest, so most tests run on both platforms.

Known starting state

Fresh install for onboarding tests, logged-in session for the rest, and no test depends on run order.

Test what phones do

Rotation, backgrounding mid-payment, slow networks, permission prompts, notifications.

A device matrix

One emulator per push; the full suite across real devices on BrowserStack before release.
